# /deploy-sales-insights — Design (draft, 2026-11-05)

Status: **built; first full deploy to `aio-dev` passed verify (2026-11-05).** 171 semantic objects, 68 vizzes, 6 dashboards; all 471 widgets and 128 dynamic tokens `Ok`; all 7 metrics return data. Spike scripts are in `/tmp/si_spike/`.

## 1. Goal and scope

Any SE runs `/deploy-sales-insights` against any Salesforce org with Data Cloud, with no managed Sales Insights app, and gets the original Sales Insights dashboards populated with believable synthetic data.

- **Source of truth:** the original Sales Insights in the Tableau Next & Slack org (`ExtendedSalesInsights` SDM, workspace `Sales_Insights`). Salesforce CLI alias `tab-next-and-slack-org-yvh6i7`.
- **Dashboards (6):** Sales Performance, Team Performance, Leaderboard, Sales Stage Progression, Sales Stage Conversion, Lead Analysis. Homepage is custom and excluded.
- **Data:** fixed, generic and seeded at first. Customer customization comes later, through a config file.
- **Not in scope:** Forecasting dashboard variants, the rest of the `ExtendedSalesInsights` SDM (Case, Agent Work, Email and so on), and any managed-app dependency.

Objects: Opportunity, Opportunity_History, Opportunity_Historical_Trend, Lead, Account, User, User_Role_Flattened, Business_Period, Forecasting_Fact, Contact_Point_Address, Opportunity_Stage, Product. The trace doesn't list three more, but they're required:
- **Opportunity_Product.** It's the bridge table Product joins through.
- **Calendar_Event + Task.** They feed the `Activity_lv` union, which drives `Count_Flag_RI_clc` → `No_Activity_Dynamic_clc` → the Leaderboard "No Activity" tab.

Logical views: `Activity_lv` (union) and `DateDimSQL` (custom-SQL date series, needs no data). Opportunity and Lead join to `DateDimSQL` through calc dimensions, so those calcs must exist before the relationships.

## 2. Layout in git

Modeled on `revintel/`. Everything lives outside the gitignored `demos/`.

```
salesinsights/
  __main__.py          CLI: python3 -m salesinsights capture|generate|deploy|status|reset
  capture.py           maintainer only: source org → package
  generate.py          seeded synthetic data → CSVs
  deploy.py            checkpointed deploy to a target profile
  package/
    sales_insights_package.json   trimmed, placeholder-based (6 dashboards, 68 vizzes, SDM slice)
    data_contract.json            generated by capture: tables, fields, types, keys
  DESIGN.md
.claude/commands/deploy-sales-insights.md   rewritten to drive the CLI (short, like /update-rev-intel)
```

Per-deploy state (checkpoint, generated CSVs) goes to `demos/sales_insights/{profile}/`. It's per user, so gitignored.

## 3. Capture (maintainer, run again when Sales Insights changes)

Input: the live source org (through the CLI alias), or the saved Package & Deploy captures.

1. Read the 6 dashboards, their vizzes and the `ExtendedSalesInsights` SDM.
2. Run the dependency trace (now `/tmp/si_inventory/trace.py`). It covers viz fields, filter/parameter/metric widgets, dynamic tokens, metric references and recursive calc expressions, plus relationship-join calcs and LV members, which the current trace misses.
3. Trim the SDM to that slice, and switch each DO from `Dmo` (`ssot__X__dlm`) to `dlo` with a placeholder DLO name.
4. Turn org-specific values into placeholders: `{{SDM_API_NAME}}`, `{{SDM_ID}}`, `{{SDM_LABEL}}`, `{{WORKSPACE_API_NAME}}`, `{{VIZ_NAME_*}}`, `{{DLO_*}}`. Strip read-only keys (`id`, `createdBy`, `status`, `permissions`, …).
5. Write the package and `data_contract.json`. The new contract replaces the stale one in `demos/sales_insights_packages/`.

The placeholder scheme borrows from the payload another user shared as a format reference. Nothing else from that file is used.

## 4. Synthetic data (`generate.py`)

- **Seeded and fixed:** the same seed produces the same data for every SE.
- **Anchored to the generation date.** Calcs use `TODAY()` ("this quarter", "last 7 days", days in stage), so dates are written relative to today. They can't be self-healing the way Tableau Next demos are, because the dashboards reference the raw date fields directly. A `refresh` command regenerates and re-upserts with the same keys. That's the Sales Insights counterpart of `/refresh-dates`.
- **Org shape (confirmed):** 1 sales leader, 3 managers and about 12 reps, with a matching `User_Role_Flattened`.
- **Volume:** about 2,000 opportunities over 24 months. Each has stage history rows, weekly `Opportunity_Historical_Trend` snapshots, monthly quota targets (`Forecasting_Fact` × `Business_Period`), about 1,500 leads and activities on most open deals.
- **Baseline story (confirmed):** generic but drillable. One team is behind on quota. Pushed and stalled deals cluster with two reps. One lead source converts well and another converts badly. A handful of open deals have had no activity in 30+ days, which gives the No Activity tab something to show.
- **Validation:** check every column in `data_contract.json` and every join key, and confirm each dashboard filter value has rows (`data_validator` style). Fail loudly.
- **Later:** a customer config (company, industries, product families, rep names, story knobs) reusing the pattern from `revintel/`.

## 5. Deploy (`deploy.py`)

`python3 -m salesinsights deploy --profile <key>`. Checkpointed, and resumable from any phase.

| Phase | What it does |
|---|---|
| 0 Preflight | profile auth, Data Cloud on, ingest connector present (`org_bootstrap.ensure_ingest_connector`), warn if a Sales Insights workspace exists. **Refuse to deploy to the source org** (the `ExtendedSalesInsights` SDM exists there). The `default` profile, labeled "Tab Next Dev", points at it. |
| 1 Data | generate → register schemas (Text/Number/Date/DateTime/Boolean all work) → create streams → wait ACTIVE (+30s) → bulk upsert → wait `JobComplete` (Opportunity took ~6 min for 20 rows) |
| 2 Workspace + SDM | create both; DOs inline with `dataObjectType: "Dlo"`, explicit `semanticDimensions`/`semanticMeasurements` that use the **source's apiNames** (kept as-is, S1); read back `apiName` and `id` |
| 3 Semantic layer | **v66.0**: parameters → calc dims → calc measures → logical views → relationships → metrics, all posted **verbatim from the capture**. Strip `baseModelApiName`/`id`/`logicalViewId` and setterless read-only keys such as `dataDefinedGoals` (omit them; don't send `[]`). Relationships use `criteria[].leftSemanticFieldApiName` |
| 4 Vizzes | 68, posted verbatim through REST v67.0 `minorVersion=14` with placeholders resolved (S6) |
| 5 Dashboards | **one POST each** (v67.0 `minorVersion=14`) with all widgets inline: text + dynamic tokens, metric tiles, filters, parameters, summary, buttons (S5). Metrics must exist first: the API accepts a tile for a missing metric and it reads back as `DataSourceError` |
| 6 Verify | GET each dashboard and require every widget and token `status: "Ok"`; query the 6 metrics and a few known values through `POST /services/data/v65.0/semantic-engine/gateway` (`structuredSemanticQuery` / `structuredMetricQuery`) |
| 7 Finish | business preferences through MCP; workspace sharing is manual in the UI (API rejects it) |

Phase 1 reuses `web-ui/builder.py`'s ingest code (the only shared implementation of `/api/v1/ingest/jobs`) rather than adding another one. The ingest helpers may need to move into a root-level module first.

Asset safety: the checkpoint tracks every created asset. `reset` deletes only what's in the checkpoint.

## 6. Decisions (confirmed 2026-11-05)

1. **Generate Activity data (Calendar_Event + Task): yes.** Two small tables keep the Leaderboard "No Activity" tab working. Dropping `Count_Flag_RI_clc` would break that whole tab. The union joins to Opportunity on `Task_Related_To_Item`, so **only Task rows count**. Calendar Event has no related-to field (same as the source); a few rows are enough for the union to exist.
2. **Vizzes: REST, verbatim** (S6 passed). Full-spec REST (v67.0, `minorVersion=14`) keeps dual-axis, colors and formatting in one pass. This is a documented exception to Guideline 10 (we're copying exact specs, not building from intent).
3. **Keep the source's names: yes** (S1 passed). DO and field apiNames are kept exactly, so every calc expression, viz field, filter and token works unchanged. **No reference translator is needed.**

## 7b. Lessons from the first deploy

- Data objects copied from DMOs: drop `standardDataObjectName` and field `storageDataType` (DLOs reject them), but **keep `tableType: "Shared"`** on Account, Contact_Point_Address, Product and User. Lead and Opportunity both join those tables, and without `Shared` the second join is rejected as cyclic.
- Semantic string comparisons are case-sensitive. The data stores flags as lowercase `true`/`false` like the source, and `SOURCE_FIXES` corrects the one calc that compared against `'False'`.
- Source calc quirks found by comparing metrics with the original (same queries against `ExtendedSalesInsights`):
  - `Average_Days_to_Close_RI_clc` and the two `LA_Lead_Age` calcs compute `DATEDIFF(later, earlier)`, which is negative on realistic data. The original shows positive values only because its replayed data has deals created after they closed.
  - `Open_pipeline_RI_clc` is `MAX({FIXED opp, created : SUM(...)})`, so the "Open Pipeline" BAN is the largest single Pipeline history row (source: $1,588,400 = its largest deal).
  - `Average_Deal_Size_mtc` reads 2–4× below the true average through the date-dimension join, in the original as well.
